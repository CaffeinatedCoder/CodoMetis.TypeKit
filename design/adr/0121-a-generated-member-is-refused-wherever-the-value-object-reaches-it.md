# 0121. A generated member written by hand is refused wherever the value object reaches it

Date: 2026-10-30
Status: accepted

Context: [#191](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/191), under the 2.3.1 epic
[#198](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/198), found while
[#188](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/pull/188) closed the same gap for the arithmetic
operators, where an interface's explicit implementation is kept, from an outside review of that pull request;
widened the same day by [#195](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/195) and
[#197](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/197), from a second outside review; refines
[decision 28](0028-seams-declared-everything-else-refused.md), and is an exception to
[decision 34](0034-errors-fixed-within-major-version-warnings.md), taken in a patch release. Decision 28 refuses a member the
generators introduce written by hand, and an explicit implementation of an interface they implement, on the value
object and, since phase 11, on a base record (CMTK1011, CMTK1008 for the comparison interfaces).
`ValueObjectDeclaration` listed the value object's members for the first, and the value object's and its base
records' for the second, and `CreateDeclarations` the value object's own.

## What was measured

On `release/2.4.0` at `97c87c1`, 2026-10-30, with a consumer of the generators, the code these members are
generated by unchanged since 2.3.0 (`v2.3.0`, edeb90c), which 2.3.1 patches:

- **An interface's explicit implementation was replaced without a word.** An interface can implement a member
  of a base interface explicitly, and every type that declares it reaches that default until it declares a
  public member of its own. The generated member is one, for each of the eleven interfaces the generators
  implement: `IFormattable`, `ISpanFormattable`, `IUtf8SpanFormattable`, `IParsable`, `ISpanParsable`,
  `IUtf8SpanParsable`, `IMinMaxValue`, `IComparable`, `IComparable<T>`, `IComparisonOperators` (each answered
  the generated member's result through a generic call, where the interface's threw or answered its own) and
  `IConvertible` (below). The same held two interfaces down and through an interface of a base record.
- **Another assembly's were missed too, a base record's included.** Metalama lists no private member of a type
  in another assembly, and an explicit implementation is private, so the listing saw none in a referenced
  project. An interface there was replaced as above. A base record there was replaced or kept answering the
  interface: an `IFormattable` call on a value object over a referenced record that implements it printed `1`,
  where the base answered its own text, and `Max<T>()` over a referenced `MinMaxBase<TSelf>` reached the base's,
  which threw. A closed set over a referenced base class that implements `IClosedSet<TSelf>` explicitly listed
  two members in `All` and none through `T.All`, named `Red` "base" through the interface, and EF Core stored
  "base" and read no member's name back. The rule has had this gap since phase 11.
  `INamedType.TryFindImplementationForInterfaceMember` finds every one of them.
- **A base record's public member counted for nothing** (#197). Its public static `MinValue` and `MaxValue`, with
  `IMinMaxValue<TSelf>` or without, were the value object's, and no `MinValue` or `MaxValue` was generated. Its
  public `Value`, `From`, `Parse`, `TryParse`, `ToString(string?, IFormatProvider?)`, `TryFormat` or
  `CompareTo(object)` failed the aspect (LAMA0500), naming nothing the user wrote. From another assembly, a
  public static member that implements a static abstract one reads as an explicit implementation, since the
  compiler records every such implementation as one, so it was refused as "the explicit implementation of ...".
- **A base record's `Create` gave two rule sets** (#195). Where the value object reaches the marker only through
  a base record of another project that implements `Create` explicitly, `TryFrom("x")` ran the value object's
  `Create`, which accepted, and generic `T.Create("x")` the base's, which refused. Declaring the marker on the value
  object as well re-implements it, and both agree. In the same project such a base carries the marker and is
  refused already (CMTK1022).
- **`IConvertible` declared through an interface** failed the aspect (LAMA0041), as declaring it directly did
  before CMTK1011 named it. So did a closed set's `IParsable<TSelf>` declared through an interface (LAMA0512). A
  closed set's interface that implements `IClosedSet<TSelf>.Name` or `TryParse` explicitly was replaced by the
  generated members without a word.
- **An interface's `==`, `!=` and `IEquatable<T>.Equals` are replaced by the record's own**, in a plain record
  as in a value object, so the generators change nothing there. For the same reason
  `ValueObjectContractAspect.ExplicitlyImplementsEquatableBetween` has no gap: a base record's synthesized
  `Equals(TBase)` implements `IEquatable<TBase>` before any interface's default (a `HashSet` of the base held
  both value objects).
- **.NET implements three such members itself**: `INumberBase<TSelf>` implements `IUtf8SpanFormattable.TryFormat`
  and `IUtf8SpanParsable<TSelf>.Parse` and `TryParse` explicitly, as bridges to the UTF-16 members. A scan of the
  interfaces of `System.Private.CoreLib` for explicit implementations of the eleven found no other; the reference
  assembly carries the same three.

## Decision

**CMTK1011, and CMTK1008 for the comparison interfaces, refuse a member the generators introduce wherever the
value object reaches it**: written on it, or in a base record, public or explicit, or as an explicit implementation
in an interface it implements, directly or through another, in this assembly or another. The error names the
member and where it is, "in its base type `X`" or "in its interface `X`", and a public member by its own name,
never as an explicit implementation. A closed set's `IClosedSet<TSelf>` is held the same way.

- **Found by the interface mapping, never by listing members.** For each member of a generated interface the
  value object implements, `TryFindImplementationForInterfaceMember` gives the implementation C# maps it to; one
  other than the value object's own public member is refused. The record's own `==` is what the mapping finds for
  an interface's `==`, so that case needs no rule of its own. A base record's public member of a generated name
  that implements no interface is found by the same names and signatures as on the value object.
- **A base record's `Create` counts.** One the value object reaches through the marker, explicit or beside its own,
  is CMTK1011, which says to declare the marker on the value object itself. A base's public `Create` alone is one
  rule set, which the generated code calls too, and builds.
- **`IConvertible` and a set's `IParsable<TSelf>` declared through an interface** are CMTK1011, naming the
  interface, where the aspect failed.
- **Not refused: an interface's explicit implementation of a member of an interface of its own library.** That
  is .NET's `INumberBase<TSelf>`: every .NET number replaces its bridges with its own UTF-8 members, as the
  generated ones do, and refusing them would leave no value object able to implement `INumberBase<TSelf>`. The
  test is by assembly symbol, never by name.
- **Not this decision:** `IValueObject<,>`, `IValueObjectMaterializer<,>` or `IPlainValueObject<,>` declared
  through an interface of the user's still fails the aspect (LAMA0512,
  [#192](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/192)). A seam inherited from a base record,
  `CompareTo(TSelf)` and `TryFrom` among them, is
  [#194](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/194)'s, and a hand-written `Equals(TBase)`
  [#196](https://github.com/CaffeinatedCoder/CodoMetis.TypeKit/issues/196)'s.

**The exception to decision 34.** A build that worked on 2.3.0 can fail on 2.3.1: a value object or a closed set
that reaches an interface's explicit implementation of a generated member, or a base record's in another
assembly; a value object over a base record whose public `MinValue` or `MaxValue` stood in for the generated one;
and one whose generic `T.Create` reached a base's `Create` beside its own. Each is code that never runs (an
interface's default the generated member replaced) or a second answer beside the generated one (a base's kept
member), in every build that contains it, so the error names a defect, never correct code. The defect shipped in
2.3.0, so its fix ships in the patch 2.3.1, not in a minor: waiting would keep a wrong answer in every 2.3 build,
and decision 119's reason, an error that names a defect in every build that contains it, holds after a tag as it
does before one. The changelog's Changed section says which
declarations fail and what to write instead. The forms that failed the aspect before fail the build with a CMTK
error now, which breaks no build.

`BuildOutcomeTests` holds it: one value object per interface, two interfaces down, through a base record's
interface, a record class over a reference type, and from another assembly (`IProbeFormats`, `IProbeBounded`,
`IProbeOrders`, `ProbeFormattableRecord` and `ProbeMinMaxRecord` in `CodoMetis.TypeKit.Generators.Probes`); a
base record's public member of each kind, in this project and in a library the generators do not run in, which
the fixture builds beside its consumers; a base record's `Create`; a closed set through an interface of either
assembly and over the library's base class; and the cases that build: a `ToString()` seam, a `Uri`'s missing
ordering, an interface's `==`, an `INumberBase<TSelf>` value object, and one `Create` over a base record.
